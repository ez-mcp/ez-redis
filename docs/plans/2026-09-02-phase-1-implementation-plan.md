### D.1 Execution semantics
- `pre-commit install` once per clone (documented in the plan-of-record's CONTRIBUTING stub, Phase 45 finalizes).
- pyright hook runs `pyright --strict` via the project venv (pyright-python resolves the environment; verified behavior — if the hook's environment resolution misbehaves with uv-managed venvs, fall back to a `local` hook running `uv run pyright` — **documented fallback, decided at execution with evidence**). `[REC]`
- Expected runtime on this package: ruff < 0.5 s, pyright ~1–2 s, gitleaks < 1 s. Total commit-time overhead ≈ 2–3 s — well inside "never a hindrance". `[INF]`
- **Offline developers (proactive):** pre-commit and gitleaks fetch remote hook repos on first run. A contributor behind a proxy runs `pre-commit install --install-hooks` once with proxy env set; after that, runs are offline. **No hook may ever silently skip** — if the gitleaks binary or any hook environment is unavailable, the hook fails loudly (never `staged_files` bypass, never `--no-verify` normalization). `[DECISION]`
- **pyright hook environment (v2.0):** if the `pyright-python` hook misresolves the uv-managed venv, the documented fallback is a `local` hook running `uv run pyright`. Decided with evidence at execution, never silently. `[REC]`

### D.2 gitleaks allowlist tuning
`.gitleaks.toml` extends the default rules with an allowlist for `tests/fixtures/**` (Phase 3's `secrets-app` fixture contains *deliberate* fake credentials like `redis://user:pass@host`) — scoped by path + regex so real secrets in `src/` are never exempted. ## Part F — `src/ez_redis/logging.py` (full specification)

### F.1 Contract (from parent plan Phase 1, binding)
- JSON lines → **stderr only**.
- Level from `EZ_REDIS_LOG_LEVEL` (default `WARNING`).
- Fixed field set: `ts`, `level`, `event`, `component`, plus explicitly allowed context keys.
- A filter drops any field whose key is tagged as content (`content`, `excerpt`, `prompt`, `snippet`) — accidental logging of file text must be impossible.

### F.2 Design (structlog, per D-P1-6)
```python
import logging, sys
import structlog

CONTENT_KEYS: Final[frozenset[str]] = frozenset({"content", "excerpt", "prompt", "snippet"})
ALLOWED_CONTEXT_KEYS: Final[frozenset[str]] = frozenset({"repo_root", "tool", "rule_id", "path", "cap"})
FIXED_FIELDS: Final[tuple[str, ...]] = ("ts", "level", "event", "component")

def configure_logging(level_name: str | None = None) -> None:
    """Configure structlog for JSON-lines output on stderr. Idempotent."""
```

- Processor chain (v2.0 ordering): `merge_contextvars` → `add_log_level` → `TimeStamper(fmt="iso", utc=True)` → **content-key filter** (custom processor that removes any key in `CONTENT_KEYS`, case-insensitively) → **allowlist filter** (fixed fields + `ALLOWED_CONTEXT_KEYS` + `dropped_keys` only) → `JSONRenderer()`. The two filters run **last before rendering** so no earlier processor can resurrect a dropped key.
- **Log-injection defense (v2.0):** `JSONRenderer` escapes embedded newlines, so a value containing `\n` can never forge a second log line; `test_newline_in_value_stays_single_line` proves it.
- **Stdout purity (v2.0):** the stderr stream is captured **at configure time**, not lazily, so a later `sys.stdout`/`sys.stderr` swap cannot divert output; `test_stdout_untouched` asserts stdout stays byte-empty (INV-3).
- **Dropped-key note (v2.0):** dropped content keys are surfaced as `dropped_keys: [names…]` in the event dict — key **names only, never values** (SR-1/SR-2). Emitted in-band instead of a nested log call to avoid processor recursion.
- **Pyright-strict guidance (v2.0):** structlog ships `py.typed`; processors are typed via `structlog.typing.Processor` / `EventDict`. Wrap `structlog.get_logger()` in a module-private typed helper returning a concrete `BoundLogger` so strict mode stays clean project-wide **by typing, not by `# pyright: ignore`**. This is the only anticipated friction point.
- The filter runs **last before rendering** so no processor can re-introduce a dropped key.
- Output stream: `logging.StreamHandler(sys.stderr)` wrapped via `structlog.stdlib.ProcessorFormatter`, so stdlib loggers (e.g., from `mcp`) are captured into the same JSON format.
- `logger = structlog.get_logger(component="...")` at module level in consumers; `component` is part of the fixed field set.

### F.3 Behavior table

| Input | Behavior |
|---|---|
| `EZ_REDIS_LOG_LEVEL` unset | `WARNING` |
| Valid value (`DEBUG`/`INFO`/`WARNING`/`ERROR`/`CRITICAL`, case-insensitive) | that level |
| Invalid value (e.g. `LOOG`) | **Fail loudly**: raise `ConfigError` naming the variable, the bad value, and the valid set (C7, D-P1-11) |
| Event kwargs containing a content key | key silently dropped from output; a `debug`-level note `dropped_content_key=<name>` is emitted (name only, never the value) |
| Key not in `ALLOWED_CONTEXT_KEYS` | dropped (fixed field set enforced) |

## Part H — `src/ez_redis/config.py` (full specification)

### H.1 Contract (from parent plan Phase 1, binding)
Typed reader for `EZ_REDIS_DISABLE_HOOKS`, `EZ_REDIS_LOG_LEVEL`, `XDG_CACHE_HOME` fallback rules.

### H.2 Public API (shapes, not signatures — implementer owns exact form)

| Symbol | Kind | Semantics |
|---|---|---|
| `ConfigError` | exception | Project base for config failures; actionable message, names the variable |
| `read_log_level() -> str` | function | Validated level name; raises `ConfigError` on invalid (D-P1-11) |
| `hooks_disabled() -> bool` | function | True iff env value (case-insensitive) ∈ `{"1","true","yes","on"}`; unset/empty/anything else → False (D-P1-12) |
| `cache_dir() -> Path` | function | `$XDG_CACHE_HOME/ez-redis` if `XDG_CACHE_HOME` set **and** absolute; else `~/.cache/ez-redis`; never creates the directory (creation is the caller's job, Phase 33) |
| `load_config() -> Config` | function | Frozen dataclass aggregating the three; single construction point for consumers |

### H.3 XDG fallback rules (precise)
1. `XDG_CACHE_HOME` set and value is an absolute path → use `<value>/ez-redis`.
2. `XDG_CACHE_HOME` set but relative or empty → **ignore it** (XDG spec: "must be absolute"; non-compliant values fall back to default) and use `~/.cache/ez-redis`. `[EXT: XDG Base Directory Specification §2]`
3. Unset → `~/.cache/ez-redis`.
4. `Path.home()` unresolvable (rare; e.g. stripped env) → raise `ConfigError` with actionable message. Fail loudly (C7).
5. **Windows note (v2.0, D34 best-effort):** `XDG_CACHE_HOME` is often unset there — the fallback is `Path.home() / ".cache" / "ez-redis"`; acceptable for v1, and `doctor` (Phase 44) surfaces the resolved path.

## Part K — Failure Modes & Pre-Mortem

| Failure mode | Handling |
|---|---|
| `uv` not installed on a contributor machine | README/CONTRIBUTING (Phase 45) documents install; Phase 1 PR description includes the one-line install command |
| pyright hook + uv venv mismatch | Documented fallback: `local` hook running `uv run pyright` (§D.1); decided with evidence at execution |

| `EZ_REDIS_LOG_LEVEL` set in user shell to garbage | `ConfigError` at first logging use with actionable message — loud, not silent (D-P1-11) |
| Developer commits a real secret | gitleaks blocks at commit; if it ever lands, rotation is mandatory (security doctrine §5) — documented in CONTRIBUTING (Phase 45) |

## Part M — Security Review (Phase-1 scope)

- **Trust boundaries touched:** environment variables (host-controlled) → parsed by `config.py` with whitelist semantics (D-P1-12), never interpolated into paths or commands; `XDG_CACHE_HOME` validated absolute before use (path-traversal hygiene per security doctrine §4).
- **Secrets:** gitleaks at commit time; logger drops content-tagged keys by construction (INV-2); no secret-like file is ever opened by Phase-1 code (it opens nothing).
- **Supply chain:** two runtime deps, both pinned with caps in `uv.lock`; dev deps capped; gitleaks binary managed by pre-commit with pinned rev.
- **Fail-closed vs fail-open:** config errors fail loudly (C7); nothing security-relevant is gated on logging or config success.

**Security risk register (v2.0):**

| # | Risk | Abuse case | Defense |
|---|---|---|---|
| SR-1 | Secret leaks through log context values | future phase logs kwargs containing `redis://user:pass@host` | content-key filter + allowlist-only context keys (whitelist, not blacklist) |
| SR-2 | Secret under an allowed key | `path="…/prod.env"` carrying sensitive content | `path` holds confined paths only (Phase 4 contract); Phase-4 redaction gates all content before any logging call |
| SR-3 | Log injection / forged lines | value containing `\n` fakes a second entry | JSON renderer escapes newlines; dedicated test |
| SR-4 | Secret committed to the new repo | real `REDIS_URL` pasted into a test | gitleaks at commit, pinned rev; rotation-mandatory note → CONTRIBUTING (Phase 45) |
| SR-5 | Env-var value echo | `ConfigError` echoing a mistyped secret | error names variable + valid set, never the value; test |
| SR-6 | Supply chain via dev tooling | malicious hook repo / typosquatted pin | pinned revs in `.pre-commit-config.yaml`; lockfile diff reviewed per PR; pip-audit from Phase 2 |
| SR-7 | XDG path traversal | `XDG_CACHE_HOME=/etc` redirecting future writes | absolute-required check + `ez-redis`-suffixed dir; Phase 33 adds 0700 + confined filename; Phase 1 never writes |
